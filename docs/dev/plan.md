# 개발 계획

## 기술 스택 (결정)
| 항목 | 선택 | 이유 |
|---|---|---|
| 언어 | TypeScript | 타입으로 실수를 일찍 잡는다 |
| 빌드 | Vite | 빠르고 설정이 적다. 빌드 결과를 아티팩트로 올리기 쉽다 |
| 화면 | Preact (+ CSS) | 이 게임은 카드·패널·한글 텍스트가 많은 UI 중심 게임이라 게임 엔진(Phaser 등)보다 웹 UI 방식이 맞다. 도트 그림은 `image-rendering: pixelated`로 표시 |
| 규칙 | `src/core` 순수 TypeScript | 화면과 분리해 테스트로 검증 |
| 테스트 | Vitest (규칙), Playwright (화면 동작, Chromium 설치돼 있음) | `@playwright/test` 추가: 실제 폰 크기 화면에서 클릭·스크린샷으로 QA |

- 처음 제안했던 Phaser는 실시간 액션(뱀서식)일 때의 선택이었다. 턴제 카드 + CCTV 화면으로 바뀌면서 웹 UI 방식이 더 단순하고 오류가 적다.
- 검토한 다른 선택지: Unity(C#), Unreal(C++), Godot, Phaser. 편집기 중심 엔진은 클라우드에서 화면 없이 만들고 검증하기 어렵고, 이 게임은 3D·실시간 물리가 필요 없어 웹 UI 방식으로 확정 (2026-10-06, 사용자 확인).
- 출시 경로: 웹 → 필요 시 앱 포장 도구로 iOS·Android, PC(Steam).
- 나중에 연출이 많이 필요해지면 특정 화면(CCTV)만 Canvas로 그리는 식으로 확장한다.

## 마일스톤 (4주)
| 주 | 목표 | 완료 기준 |
|---|---|---|
| M1 (1주차) | **1일차 밤을 처음부터 끝까지 플레이** | CCTV 4대, 이상 현상 3~4종, 기본 카드 4종, 배터리·위험도·턴, 생존/실패 화면. 아티팩트로 플레이 가능 |
| M2 (2주차) | 낮 숙직실 + 2일차 | 수칙서 미리 읽기·의심 표시, 카드 보상, 거짓 수칙(2일차 7번), 저장/불러오기 |
| M3 (3주차) | 캡슐 기계 + 동료 | 캡슐 뽑기(확률표·천장), 동료 3명, 기념품 6개, 회차 구조(실패 → 1일차, 메모 유지) |
| M4 (4주차) | 다듬기 | 도트 아트 적용, 사운드, 공포 연출, QA·보안·수익 점검, 배포 |

## 부서별 참여 시점
- 기획: 매 마일스톤 시작 전 데이터(수칙, 이상 현상, 카드) 확정
- 디자인: M1부터 화면 구현 기준 제공, M4에 도트 아트
- 개발: 전 기간
- QA: 매 마일스톤 끝에 테스트 + 실제 화면 플레이 확인
- 보안: M2(저장 데이터), M3(가챠 확률 조작 방지), M4(배포)
- 수익: M3(가챠 구조 검토), M4(과금 모델 제안서)
